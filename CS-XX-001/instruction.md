# 含税金额精度整改

## 工程背景

你在维护一家英国线上零售商的店铺系统。代码库在 `repo/` 下，是 django-oscar 4.0 开发分支的一个快照：

- `repo/src/oscar/`：框架源码，按业务域分应用，位于 `apps/` 下，例如 `basket`、`partner`、`offer`、`order`、`shipping`、`checkout`
- `repo/tests/`：仓库自带的测试
- `repo/docs/`：文档

店铺的定价用 `oscar.apps.partner.strategy` 里的固定税率策略。标准税率是 20%。少数商品类别使用 17.5% 这类带半个百分点的税率，做法是继承 `FixedRateTax` 并设置 `rate`。

系统一直在线上运行。这次改动上线不停机，也不做数据迁移。上线那一刻，数据库里有顾客放了商品还没结账的购物车，也有已经下单、还没处理完的订单。

财务月结对账时报了两个问题：

1. 低价商品批量购买时税额丢失。单价 0.01、数量 100、税率 20%，税额应为 0.20，系统算出 0.00。
2. 购物车合计出现超过两位小数的金额。单价 9.99、数量 3，叠加一个 15% 的促销，当折扣记在含税金额上时，含税合计里出现了 30.5745 这样的数。

## 已确定的整改方向

财务和技术负责人已经确认：

1. 单件税额和含税单价在系统内部保留 4 位小数，不再提前舍入到分。
2. 金额在对外时才舍入到分。所有舍入都用四舍五入，即 `ROUND_HALF_UP`。

顾客看到的价格、据以筛选或排序商品的价格，以及购物车合计、订单和价格明细中的账面金额都以分为单位。分批发货时，同一订单行的数量和金额须能与其价格明细对账；正价发货的每一批只能收取非负金额，累计收款不能超过该行的应收金额，全数发货后两者相等。尾差可以分配到不同批次。

商品促销沿用仓库原有的业务口径。英国定价策略用含税有效单价计算百分比折扣额。对于该商品促销，`OSCAR_OFFERS_INCL_TAX` 控制算出的折扣记在含税还是不含税的行金额上。两个配置下都要对账。

## 同事的方案草稿

> 我看了一下，问题就出在两处。
>
> 第一处是 `FixedRateTax.exponent`，现在是 `D("0.01")`，改成 `D("0.0001")`。`quantize` 默认就是四舍五入，所以那两句 `quantize(exponent)` 不用动。
>
> 第二处是 `Basket._get_total`，在返回前统一用 `round_half_up` 舍入到两位。
>
> 行金额、运费、订单金额都是从这两处往下取数的。上游改对了，下游自然就对，不用逐个文件去改。

## 你的任务

直接修改 `repo/` 下的代码完成整改。同事的草稿只是参考，是否采纳、是否足够由你判断。

改完之后要守住两条底线：

- 系统中表示同一笔钱的地方必须一致，分项合计等于对应总额。各行的分位尾差可以按一致的规则分摊。
- 升级要兼容已有数据。未下单购物车继续按现行策略结算，保留加购时记录的历史单价。价格变动提示比较当时与现在顾客看到的含税单价，只有两者按分确实不同时才提示，包括因本次升级而变动一分的情形。已下单订单继续按原记录结算，保留历史订单总额、订单行、价格明细和已收款。

约束：

- 不修改已有公开类和函数的签名。
- 不改动模型字段的定义，不需要新增数据库迁移。
- 不改动商品促销的折扣算法。促销自己记录的折扣总额与各行金额之间可能出现的一分钱差异，不在这次范围内。
- 只交付代码改动，不需要写说明文档。

运行环境是 Python 3.12 和 Django 5.1。仓库自带的测试可以这样运行：

```
cd repo
python -m pytest --sqlite tests/unit tests/integration/basket
```
